1. Executive Summary & Design Philosophy
Mythos SMP is a revolutionary, custom Minecraft Paper Server experience modeled around mythological archetypes and risk-reward player dynamics. Unlike standard survival multiplayer systems where progression is vertical, static, and safe (e.g., leveling up skills or unlocking permanent perks), Mythos SMP introduces horizontal, high-stakes progression governed by the Vow System. To attain divine power, players must subject themselves to a public, highly dangerous trial that broadcasts their vulnerability to rival factions in real-time, sparking emergent PvP conflicts, dynamic defensive alliances, and strategic betrayals.
The Core Gameplay Loop & Progression Economics
The server economics and player retention loop are designed to prevent late-game stagnation by introducing complete asset-and-ability loss on death. This establishes a fluid, dynamic distribution of power across the player base. The logical flow operates as a cycle of acquisition, defense, and strategic loss:
THE CYCLICAL PROGRESSION ENGINE
1. Resource Influx: Gather rare elements (Netherite, Heart of the Sea, etc.) to craft Vow-specific scrolls.
2. Location Decryption: Extract physical coordinate rules from the scroll to locate ancient Trial Grounds.
3. Trial Initiation & Public Beacon: Trigger the trial. The plugin broadcasts the player's coordinates server-wide.
4. Survival Under Siege: Defend against 10 minutes of compounding waves of hyper-customized Mythos monsters.
5. Divine Bestowal: Secure the Vow. Enjoy permanent passives and raw active abilities, governed by a harsh Curse.
6. High-Stakes Hegemony: Dominate standard PvP/PvE, build trusted groups, or bind souls via the Seal of Union.
7. Complete Power Transfer: On death, the active power is ripped from the player. It drops as an Expired Vow Book. Rivals must successfully undergo the same trials to claim the divine abilities, initiating the cycle anew.
	

Design Psychology & Player Interactions
The design psychology focuses heavily on human-to-human dynamic structures. Traditional SMPs fail because power accumulates linearly until a single faction dominates without competition. Mythos SMP breaks this bottleneck in three ways:
* The Vulnerability of Ascendancy: Because trial coordinate broadcasts expose players, a player seeking Zeus's power cannot do it secretly. They are vulnerable. Their allies must form defensive phalanxes to block rival raiders.
* The trust Framework: The '/trust' command creates structural party groupings. Friendly fire from chaotic high-radius AOE abilities (like Zeus's Thundercrash or Hades's Call of the Reaper) is blocked for trusted members, allowing coordinate battles to be organized and tactical rather than purely chaotic.
* The Seal of Union (Double-Edged Alliances): By physically linking two players' divine status, the Seal of Union establishes heavy mutual protection. If one dies, both lose their powers. This prevents a single 'super-soldier' meta and forces players to defend their weaker, utility-based partners (e.g., Plutus or Hermes users).

Decoupled Architectural Overview
The codebase utilizes a modern architectural standard separating UI/Event handling, business logic execution, and data access layers. No direct SQL queries occur within event listeners, and no Minecraft API objects (like Player or World) are stored long-term in memory to prevent severe memory leaks.
MYTHOS EXTENSIBLE PIPELINE GRAPH
[Bukkit Event/Command Listener]
     ↓ (Captures event, validates input, acts on main thread)
[Custom Event Bridge] (Triggers VowUnlockEvent, VowLossEvent, TrialStartEvent)
     ↓ (Decoupled execution via services)
[Service Layer] (AbilityManager, TrialManager, SealOfUnionManager)
     ↓ (Launches non-blocking task on DB dispatcher)
[Data Repository] (PlayerDataManager / DatabaseManager) 
     ↓ (Atomic transaction execution)
[SQLite Persistence]
	

3. Database Schema & Data Modeling
To ensure persistent data consistency across unexpected server crashes, a standardized SQL schema is maintained. The database setup includes tables for players, active vows, player trusts, and mutual unions. Below are the production-grade SQLite/MySQL-ready schemas:
-- Core Players Table
CREATE TABLE IF NOT EXISTS mythos_players (
   player_uuid VARCHAR(36) PRIMARY KEY NOT NULL,
   last_known_name VARCHAR(16) NOT NULL,
   active_vow VARCHAR(32) DEFAULT NULL,
   cooldown_multiplier REAL DEFAULT 1.0,
   last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Trust Relations Table (Bi-directional relational index)
CREATE TABLE IF NOT EXISTS mythos_trusts (
   player_uuid VARCHAR(36) NOT NULL,
   trusted_uuid VARCHAR(36) NOT NULL,
   created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
   PRIMARY KEY (player_uuid, trusted_uuid),
   FOREIGN KEY (player_uuid) REFERENCES mythos_players(player_uuid) ON DELETE CASCADE
);

-- Active Seal of Union Table
CREATE TABLE IF NOT EXISTS mythos_unions (
   union_id VARCHAR(36) PRIMARY KEY NOT NULL,
   party_a_uuid VARCHAR(36) NOT NULL UNIQUE,
   party_b_uuid VARCHAR(36) NOT NULL UNIQUE,
   creation_timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
   FOREIGN KEY (party_a_uuid) REFERENCES mythos_players(player_uuid) ON DELETE CASCADE,
   FOREIGN KEY (party_b_uuid) REFERENCES mythos_players(player_uuid) ON DELETE CASCADE
);

-- Performance Indexes
CREATE INDEX IF NOT EXISTS idx_trust_player ON mythos_trusts(player_uuid);
CREATE INDEX IF NOT EXISTS idx_unions_lookup ON mythos_unions(party_a_uuid, party_b_uuid);
	

Data Caching & Main-Thread Safeguards
Direct SQL operations take between 1ms and 50ms depending on hardware load, which equates to a loss of 1 to 3 TPS on a production server if done synchronously. To bypass this, the PlayerDataManager maintains an in-memory concurrent map of PlayerProfile objects. Data is fetched and cached instantly on AsyncPlayerPreLoginEvent, making it fully ready when PlayerJoinEvent occurs. All writes, modifications, and background savings are executed asynchronously via a custom Coroutine Dispatcher backed by a single-threaded execution context to prevent SQLite thread contention.
4. Component Technical Specifications
4.1 PlayerDataManager
Responsible for handling memory caching and DB interactions. It maps UUIDs to internal PlayerProfile records. If a profile is modified, a dirty flag is set, and the profile is queued for the async database writer. On server shutdown, the manager blocks and flushes all dirty profiles to prevent data loss.
4.2 VowRegistry
A central registry containing registration references for all available Vows. On startup, the plugin initializes and registers all 12 Vows using a map: Map<String, Vow>. This architecture allows high extensibility, enabling third-party developers or future updates to inject custom Vows via a simple registration API. Every custom Vow class implements a base interface featuring methods for handling passives, curses, and initializations.
4.3 AbilityManager & CooldownManager
The AbilityManager intercepts /ability1 and /ability2 commands or custom keybind interact actions. It queries the player's active Vow, verifies that the user possesses the correct permission node, and delegates execution to the registered Vow ability object. Before execution, the CooldownManager checks the cooldown map (Map<UUID, Map<String, Instant>>). If an ability is on cooldown, it calculated the remaining time and dispatches a formatted Action Bar countdown via Adventure, avoiding chat spam. Cooldown states are stored as Instants in memory, ensuring they are independent of server ticks and perfectly resilient.
4.4 TrialManager
A critical engine implementing a robust state machine per trial. Each active trial instance is tracked by a TrialSession class containing state, time remaining, trial center, and custom active entity tracking list. The manager acts upon a 20-tick global scheduler, handling:
* Wave Spawning: Triggers wave transitions every 60 seconds, scaling monster attributes, armor, and traits exponentially.
* Boundary Management: Triggers immediate disqualification if the participant crosses the designated trial arena boundaries.
* Broadcast System: Flashes server-wide coordinates, updating active coordinates on boss-bars to invite PvP interference.
4.5 TrustManager & SealOfUnionManager
The TrustManager controls relational structures, returning true or false checks when checking targeting conditions within AOE calculations. The SealOfUnionManager handles high-stakes linking. When a player dies, the death event handler alerts the SealOfUnionManager. The system verifies if the victim is bound, immediately locates the surviving partner's UUID, strips their Vow, notifies them via a chilling screen title, and cleanly terminates the database row. This cascading logic is fully atomic.

6. Development Roadmap & Milestones
To execute a stable, feature-complete release, development is segmented into seven disciplined phases. Each phase represents a logical package of work with designated testing criteria:
Phase 1: Foundation (Weeks 1-2)
Deliverables: Establish Kotlin + Gradle wrapper, paper API artifacts, and SQLite database schemas. Build core command framework (/vow, /trust), local profile caching mechanisms, and localized testing environments.
QA Acceptance Benchmarks: Verify zero database write blockages on join/quit, perfect offline player data cache resolutions.
Phase 2: Core Framework (Weeks 3-4)
Deliverables: Create abstract classes for Vows, Passives, and Abilities. Implement dynamic active-listener registry maps, cooldown handlers, and custom events. Design and thoroughly QA the Vow of Ares as the foundational test.
QA Acceptance Benchmarks: Verify correct cooldown updates in action-bars, event-handling prioritization, and Ares low-health damage scaling.
Phase 3: Trial Engine (Weeks 5-6)
Deliverables: Develop custom item registries for scrolls. Construct state-machines for trials, entity tracking lists, mob attributes scaling formulas, and geographic boundary checks. Write coordinates broadcasting modules.
QA Acceptance Benchmarks: Run 10 consecutive simulated trials with up to 4 concurrent players on active trials, ensuring clean trial failures/rewards.
Phase 4: Multiplayer (Week 7)
Deliverables: Incorporate the Trust System checks inside entity-damage algorithms. Code the Seal of Union linking structures, persistent UUID-mapping databases, and cascading double-loss event algorithms.
QA Acceptance Benchmarks: Perform intensive PvP tests. Verify trusted players take 0 AOE damage. Test Union double-loss checks during sudden disconnects.
Phase 5: God Expansion (Weeks 8-10)
Deliverables: Flesh out, code, and test the remaining 11 custom Vow mechanics, YAML configs, and localized particle effect rendering scripts.
QA Acceptance Benchmarks: Verify each vow functions cleanly without performance bottlenecks in multi-entity fights.

7. Security, Exploit Prevention & Optimization
To ensure the integrity of a highly competitive SMP, security systems are established specifically targeting classic Minecraft exploit vectors and multiplayer abuse:
Combat Logging Mitigation during Trials
A critical vulnerability occurs if a player activates a trial and simply disconnects when cornered. The TrialManager handles the PlayerQuitEvent explicitly. If an active trial participant leaves the server, their trial is instantly set to 'Failed'. To punish exploiters, a custom penalty is applied: when they reconnect, the plugin immediately subtracts 40% of their base max health (or kills them directly if configured), and spawns 3 aggressive trial wardens at their location. All items stored inside their trial scroll are fully consumed and lost forever.
Seal of Union Circular Reference Defenses
Without rigorous mathematical checks, malicious players might attempt to construct circular or chained Union bonds (e.g., Player A bound to Player B, Player B bound to Player C). This would lead to a devastating infinite recursion loop on death, triggering a complete server crash. The SealOfUnionManager enforces a strict two-node graph structure. Before binding two players, the algorithm evaluates: 'Is Player A already in a union?' and 'Is Player B already in a union?' If either query returns true, the transaction is forcefully aborted, throwing a clean warning message.
Vow Book Duplication & Exploit Protection
Since Vow Books are dropped on death, they present a high target for duplication exploits. To mitigate this, every Vow Book is assigned a cryptographically secure UUID generated via java.util.UUID.randomUUID() and stamped natively into the ItemStack's PersistentDataContainer. When a player attempts to activate a book, the plugin checks the UUID against a set of 'Redeemed Book UUIDs' stored in the database. If the book UUID has already been registered or redeemed, the book is dissolved on the spot, and a secure logger alert is dispatched to administrators.
High-Performance Entity & Particle Budgeting
Under 70 concurrent players, raw particle rendering and mob AI tracking can easily cause client and server lag. Mythos SMP resolves this using dynamic budgeting systems:
* Particle Budgeting: All active particles (like Ares's aura or Boreas's Blizzard) are rendered using customized asynchronous tasks and sent exclusively to players within visual range (using Paper's World.spawnParticle with player filters), saving server packets and rendering overhead.
* Mob AI Brain Throttling: Mobs spawned during trials utilize optimized Paper EntityPathfinders. Unnecessary AI components (such as wandering or long-term memory targeting) are completely stripped out. Monsters are locked into target-seeking the trial participant, drastically minimizing pathfinding calculation loops.
